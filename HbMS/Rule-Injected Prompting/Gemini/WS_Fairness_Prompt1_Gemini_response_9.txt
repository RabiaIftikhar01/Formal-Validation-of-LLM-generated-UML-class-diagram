' Design Practices and Instructions followed:
' 1. Simplicity: Core components identified, logical separation into cohesive modules.
' 2. Naming: PascalCase for classes, singular nouns, no spaces, e.g., Patient, Bill.
' 3. Short Names: Descriptive and concise class names.
' 4. Consistency: Naming conventions applied uniformly across classes, attributes, and methods.
' 5. Attribute Assignment: Carefully assigned attributes to relevant classes, avoiding bloated structures.
' 6. Operations: Each class encapsulates behavior with meaningful operations.
' 7. No operation classes: Avoided; all classes have defined responsibilities and methods.
' 8. Manageable Responsibilities: Responsibilities are clearly divided (e.g., BillingService for orchestration, PricingEngine for pricing, Strategy classes for policies).
' 9. Access Methods: Public getters/setters are provided for attributes that need to be accessed or modified externally.
' 10. Operation Categories: Access specifiers (+ for public, - for private) categorize operations based on usage.
' 11. Reduced Relationships: Only essential relationships are modeled to reduce complexity and improve maintainability.
' 12. Unidirectional Associations: Preferred where logical and sufficient (e.g., Bill -> Patient, ChargeLineItem -> Service).
' 13. No Multi-level Inheritance: Inheritance is kept to a single level for the Service hierarchy.
' 14. No Circular Dependency: Logical separation of concerns helps prevent circular dependencies.
' 15. Multiplicity: Clearly defined for all associations, representing business rules (e.g., "1" for mandatory, "*" for many).
' 16. Relationship/Role Names: Used where they add clarity and explain the purpose of the relationship (e.g., "isFor", "contains").
' 18. Relationship Names (Verbs): Used as verbs or verb phrases.
' 20. Link Elements/Association Class: ChargeLineItem acts as an association class capturing details between Bill and Service.
' 21. Identify Relationships: Relationships are clearly identified and typed (association, inheritance, implementation).
' 22. Standard UML Notations: Standard PlantUML notations used for classes, interfaces, inheritance, and associations.
' 23. Descriptive Names: Classes, attributes, and methods are named descriptively to clearly convey their purpose.
' 24. Consistent Style: Uniform naming conventions and layout enhance readability and understanding.
' 25. Explanatory Notes: Added notes to clarify complex sections, design patterns, and workflow.
' 26. Avoid Redundancy: Removed redundant attributes (e.g., patientId from Bill, relying on association).
' 27. Loose Coupling: Achieved through the use of Strategy patterns for billing and pricing, and dedicated service classes, promoting modularity and extensibility.
